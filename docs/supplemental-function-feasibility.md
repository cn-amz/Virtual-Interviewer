# 补充功能报告与可行性分析

更新日期：2026-07-07

## 1. 第一性原理结论

虚拟面试官的核心价值不是“能聊天”，而是让用户完成一次可信的训练闭环：

```text
目标岗位与简历输入
-> 面试官提出岗位相关问题
-> 候选人回答
-> 面试官追问、澄清、压测
-> 记录证据
-> 生成复盘报告
-> 更新个人能力树
-> 给出下一次训练任务
```

因此，系统的优先级应该围绕三个问题排序：

1. 用户是否感觉自己真的被面试，而不是被 AI 助手陪聊。
2. 面试后的评分、报告和能力树是否能用面试证据解释。
3. 比赛评委是否能在短时间内看到 LLM、RAG、Function Calling、Agent 规划执行和阿里百炼 API 的真实落地。

当前项目已经打通了文本与语音雏形、登录工作台、百炼文本模型、Qwen-Omni-Realtime 事件链路和能力树原型。下一阶段最该补的是“可信证据闭环”，而不是继续堆页面或重型平台能力。

## 2. 当前没有充分考虑但应该补上的内容

### 2.1 面试证据账本

当前实时 WebSocket 事件主要在前端事件流里展示，后端没有把完整 transcript 和模型事件持续写入一个面试证据账本。报告生成如果不读取真实 transcript，就无法解释评分。

建议新增最小事件存储：

```text
data/interviews/{interview_id}.jsonl
```

每行记录一个结构化事件：

```json
{"ts":"2026-07-07T10:00:00Z","speaker":"candidate","type":"transcript.item","text":"...","metadata":{}}
```

优先记录：

- 面试官问题。
- 候选人最终转写。
- 模型追问文本。
- 工具调用结果。
- 评分证据引用。
- 关键错误和回退路径。

### 2.2 模型辅助评分与报告

当前 `services/api/app/scoring.py` 仍是确定性 MVP 评分，主要依赖回答长度、关键词和数字；`services/api/app/reporting.py` 的 summary、target_gaps、next_practice_plan 也偏模板化。它适合打通链路，但不适合作为最终比赛展示。

建议保留确定性评分作为离线 fallback，但默认报告路径升级为：

```text
transcript + JD + profile context + rubric
-> qwen3.6-plus / 可用 Qwen 文本模型
-> JSON 结构化评分
-> evidence-based report
-> ability tree changes
```

报告必须包含证据：

- 维度评分。
- 对应的回答片段。
- 面试官为什么继续追问或扣分。
- 岗位能力缺口。
- 下一次训练任务。

### 2.3 面试官追问控制器

现在 prompt 已经约束面试官身份，但还缺一个更明确的“追问决策”层。真正的面试官不会在候选人没答清时直接切题，而会先判断：

```text
回答是否命中问题？
是否有个人贡献？
是否有技术细节？
是否有验证指标？
是否需要澄清术语？
是否已经追问两轮仍无实质进展？
```

建议用轻量策略，不急着写复杂状态机：

- 每轮只维护当前问题、追问次数、缺失槽位。
- 缺失槽位包括：个人动作、技术原理、参数/指标、失败案例、取舍理由。
- 如果缺失关键槽位，继续追问同一问题。
- 只有达到追问上限或回答足够完整，才进入下一题。

### 2.4 语音模式的 turn policy

当前官方 Qwen-Omni-Realtime 同时支持 WebSocket 和 WebRTC。WebSocket 更适合服务端快速集成；WebRTC 更适合浏览器低延迟语音场景。当前项目采用 WebSocket 是合理的，但现有 UI 是按钮式开始/停止麦克风，而实时 session 配置偏 VAD 自动检测，这两者要明确统一。

建议分两档：

- P0 稳定演示：按钮式 push-to-talk + Manual turn。停止麦克风时由后端提交音频并触发回复。
- P1 全双工体验：连续麦克风 + server VAD + 打断策略 + 正在听/正在想/正在说状态。

这样既保住比赛演示的稳定性，又不放弃“全双工虚拟面试官”的长期方向。

### 2.5 观测与成本控制

文字输入有延迟时，用户不知道是卡住还是模型在思考。语音模式也需要知道当前处于采集、转写、等待回复还是播放。

建议最小增加：

- `latency.started` / `latency.done` 或本地计时字段。
- 文本模式显示“已发送，等待模型回复”并记录耗时。
- 语音模式显示“正在听、正在识别、等待面试官、正在播放”。
- 每次模型调用记录 model、mode、duration_ms、fallback。

这些数据也可进入最终报告，体现工程质量。

### 2.6 部署与 HTTPS

比赛要求线上链接，公网访问不能只停留在架构预留。现阶段不建议做复杂 provider 抽象，先选一条能跑的路：

- 早期演示：Cloudflare Tunnel、frp 或 ngrok 之一。
- 稳定提交：轻量 ECS/SAE/函数计算 + HTTPS。

如果使用浏览器麦克风，HTTPS 是公网环境下的关键约束；本地 `localhost` 可调试，但不能代表最终可访问体验。

### 2.7 隐私、授权与数据边界

简历、面试录音、转写和能力树都属于敏感个人数据。下一阶段至少需要在产品和文档中说明：

- API Key 不进入前端。
- 简历/profile 默认不提交 Git。
- 录音是否保存，默认只保存转写或事件。
- 报告导出前是否需要脱敏。
- 本地演示账号与真实账号的数据隔离边界。

## 3. 可以不用或后置的内容

### 3.1 复杂多租户、组织权限和团队管理

比赛阶段不需要。私人仓库协作可通过 GitHub collaborator 解决，产品内不必做组织权限。

### 3.2 OAuth、支付、排行榜和社交功能

这些不会增强核心面试闭环，也会增加安全和合规负担。保留本地 demo 账号和轻量 session 即可。

### 3.3 图数据库或重型知识图谱后端

能力树先用 JSON 或 SQLite 足够。真正重要的是节点变化是否来自面试证据，而不是底层是不是 Neo4j。

### 3.4 实时能力树生成

能力树应该在面试后复盘生成，不放入实时通话主链路。实时链路要轻，避免拖慢语音体验。

### 3.5 WebRTC 首版落地

WebRTC 更适合低延迟全双工，但接入复杂度更高。除非 WebSocket 延迟已经明显影响演示，否则先把 WebSocket 模式跑稳，再切 WebRTC。

### 3.6 公网发布 provider 大抽象

当前只需要一个可用线上链接。不要先写 `FrpProvider`、`CloudflareProvider`、`AliyunProvider` 三套抽象。选一条部署路，脚本化即可。

## 4. 对抗性审查收束

本轮让 Claude Code 做了只读反方审查。它提出的核心批评是：当前最致命风险不是页面不够多，而是报告和能力树如果仍是原型，会削弱 AI Agent 叙事。

我接受的意见：

- 报告/评分必须从确定性原型升级到模型辅助、证据引用。
- transcript 必须后端持久化，否则报告没有可信来源。
- VAD 和按钮式停止麦克风之间存在产品/协议策略不一致，需要尽快统一。
- 公网部署不能只停留在文档预留。

我部分接受的意见：

- “删掉确定性评分”：不完全删除，保留为离线 fallback；默认路径切到模型评分。
- “状态机不用做”：不做重型 7 阶段状态机，但需要轻量追问控制器，否则面试官行为仍容易漂。
- “发布抽象全删”：不新增复杂抽象；保留当前文档里的部署预留思路，但实现上只选一条可运行路径。

## 5. 推荐补充功能优先级

### P0：比赛可信闭环

| 功能 | 目的 | 可行性 | 建议实现 |
| --- | --- | --- | --- |
| 面试事件持久化 | 让报告有真实证据来源 | 高 | JSONL 先行，后续可迁移 SQLite |
| 模型辅助评分报告 | 让复盘可信、个性化 | 高 | 复用 `BailianTextClient` 调 qwen3.6-plus |
| 语音 turn policy 修复 | 提升语音回复可靠性 | 高 | 当前按钮 UI 先走 Manual turn |
| 公网演示链路 | 满足比赛线上链接 | 中 | 先选 tunnel 或轻量 ECS，不做大抽象 |
| 错误/延迟可见化 | 用户知道模型在思考还是卡住 | 高 | 前端状态 + 后端耗时事件 |

### P1：产品训练闭环

| 功能 | 目的 | 可行性 | 建议实现 |
| --- | --- | --- | --- |
| 简历/JD 深度 RAG | 提高岗位相关追问 | 中 | 先本地 profile/qa_bank 检索，再接百炼知识库 |
| 追问控制器 | 让面试官更像人 | 中 | 缺失槽位 + 追问次数 + 当前问题 |
| 能力树变化记录 | 展示长期成长 | 中 | 每次报告产生 `AbilityTreeChange` |
| 历史报告列表 | 支持长期复盘 | 高 | 读取本地 interview/report 存储 |
| 动态 profile/JD 选择 | 不再固定一个用户/岗位 | 中 | 接入面试配置页 session |

### P2：增强体验与扩展

| 功能 | 目的 | 可行性 | 建议实现 |
| --- | --- | --- | --- |
| 连续全双工 VAD | 更接近真人电话面试 | 中偏低 | 需要打断、回声、状态机、真机测试 |
| WebRTC 接入 | 降低浏览器语音延迟 | 中偏低 | WebSocket 稳后再做 |
| 摄像头/表情观察 | 多模态亮点 | 低 | 比赛最终可作为展望，不进主链路 |
| 正式云数据库 | 支撑多人长期使用 | 中 | SQLite/JSON 稳后迁移 |
| 高级图谱可视化 | 提升展示效果 | 中 | 数据可信后再做视觉增强 |

## 6. 可行性判断

### 技术可行性

可行。项目已经有 FastAPI、React、WebSocket、百炼文本模型、Qwen-Omni-Realtime 适配、音频播放和本地存储基础。P0 补充主要是把已有链路串得更可信，而不是从零开始。

### 成本可行性

可控。文本模式继续用 `qwen3.6-plus` 或账号内可用 Qwen 文本模型，语音模式只在需要演示全双工时开启。报告评分可在面试结束后调用一次文本模型，比实时语音便宜且稳定。

### 时间可行性

P0 功能适合小步推进：

1. 事件持久化。
2. 模型评分报告。
3. 语音 turn policy。
4. 公网演示脚本。
5. UI 状态与耗时显示。

这些可以独立验证，每项都能产出明确的测试或手工验收结果。

### 比赛叙事可行性

强。最终叙事可以从“会说话的面试官”升级为：

```text
阿里百炼实时模型进行语音面试
-> RAG 检索简历和岗位证据
-> Function Calling 触发评分、报告和能力树工具
-> 面试官根据回答质量自主追问
-> 面试后形成个人能力树和下一轮训练计划
```

这比单纯实时聊天更贴合赛题要求。

## 7. 建议下一步

下一阶段不要先做更多页面。先做 P0 的“证据闭环”：

1. 后端记录真实 transcript 和模型事件。
2. 报告生成读取真实 transcript。
3. 报告评分调用百炼文本模型并输出结构化 JSON。
4. 能力树更新引用评分证据。
5. 前端报告页展示“证据片段 -> 评分 -> 能力树变化”。

这条线完成后，产品会从“可运行 demo”变成“有可信判断的虚拟面试官”。
