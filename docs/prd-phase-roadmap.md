# 虚拟面试官产品需求文档（阶段路线）

更新日期：2026-07-01
项目：Virtual Interviewer
目标场景：AI+ 创新应用大赛演示与个人面试训练

## 1. 产品定位

虚拟面试官是一个面向求职训练和能力复盘的 AI 应用。系统通过简历/JD 上下文、实时语音或文本对话、面试官身份约束、复盘报告和能力树，帮助用户完成一次接近真实技术面试的训练闭环。

项目参赛叙事重点：

- 使用阿里百炼/Qwen 能力完成文本与实时语音面试。
- 结合 RAG、Function Calling 和结构化能力树，体现 Agent 的规划与执行能力。
- 不只回答问题，而是以面试官身份进行追问、评估和复盘。
- 支持面试后的个人能力树长期生长，形成持续训练产品。

## 2. 用户与核心场景

### 2.1 目标用户

- 准备技术面试的学生或求职者。
- 希望围绕某个岗位/JD 进行针对性训练的用户。
- 比赛评委或演示观众，用于快速理解产品闭环。

### 2.2 核心使用场景

1. 用户登录或进入本地演示账号。
2. 用户在首页选择要进入的模块：开始面试、查看知识树/能力树、查看历史报告、管理简历/JD。
3. 用户选择目标岗位、简历资料和面试模式。
4. 系统以虚拟面试官身份开始文本或语音面试。
5. 面试结束后生成复盘报告，并更新用户能力树。
6. 用户在能力树中查看成长枝、薄弱枝、退化枝和目标岗位需要补齐的虚拟树枝。

## 3. 阶段一：已实现 MVP

阶段一目标是打通本地可运行的产品闭环，证明“面试对话 -> 复盘报告 -> 能力树”的基础链路可行。

### 3.1 已实现能力

| 模块 | 状态 | 说明 |

| 前端基础页面 | 已实现 | 包含设置页、面试页、报告页的 React/Vite MVP。 |
| 后端服务 | 已实现 | FastAPI 提供健康检查、WebSocket 面试、报告生成接口。 |
| Mock 面试链路 | 已实现 | 无外部 API Key 时可本地模拟面试事件。 |

### 3.2 阶段一验收标准

- 后端测试通过：`cd services/api; .\.venv\Scripts\pytest -q`。
- 前端构建通过：`cd apps/web; npm run build`。
- 本地可打开 `http://127.0.0.1:5173/`。
- 文本输入在 `TEXT_MODE=bailian_text` 下可调用百炼文本模型。
- 面试结束后可进入报告页并展示能力树原型。

### 3.3 阶段一遗留问题

- 前端页面信息架构仍是 MVP：默认直接从设置页进入面试，缺少产品首页/工作台。
- 登录系统尚未实现，当前默认单用户/本地演示。
- 能力树还只是报告页中的结果展示，缺少独立入口、长期成长视图和交互。
- 语音链路还需要完整浏览器实测，包括麦克风权限、VAD、返回音频播放。
- 部分前端文案曾出现编码污染，需要在第二阶段统一修正。
- 报告和能力树仍是确定性原型，尚未充分引用面试证据。

## 4. 阶段二：产品化入口与用户系统

阶段二目标是把 MVP 从“直接进入面试页面”升级为一个可持续使用的个人训练产品。

### 4.1 阶段二范围

阶段二包含四个核心方向：

1. 登录与用户身份。
2. 进入面试前的首页/工作台。
3. 独立知识树/能力树模块。
4. 面试前配置流程。

不在阶段二做的内容：

- 不做复杂多租户组织管理。
- 不做支付系统。
- 不做完整后台运营系统。
- 不做重型社交/排行榜。
- 不强依赖正式云数据库；可以先本地 JSON/SQLite，预留迁移接口。

## 5. 阶段二需求详情

### 5.1 登录系统

#### 目标

让不同用户拥有独立的简历、面试记录、报告和能力树，为长期训练和后续部署打基础。

#### MVP 方案

采用轻量账号体系：

- 本地账号登录：用户名 + 密码。
- 演示账号快捷进入：例如 `demo` 用户。
- 后端生成简单 session token。
- 前端保存登录态。
- 所有用户数据通过 `user_id` 隔离。

#### 后续预留

- GitHub/OAuth 登录。
- 阿里云账号或学校账号接入。
- 团队/组织权限。
- 更严格的密码哈希、刷新 token、权限角色。

#### 验收标准

- 未登录用户不能直接进入面试、报告、能力树页面。
- 登录后进入工作台。
- 用户 A 和用户 B 的能力树、历史报告互不污染。
- 退出登录后回到登录页。

### 5.2 首页/工作台

#### 目标

用户进入系统后不再直接进入面试，而是先看到一个清晰的产品入口。

#### 页面结构

工作台包含以下入口：

- `开始模拟面试`
- `查看能力树`
- `历史面试报告`
- `管理简历与岗位`
- `系统设置/模型配置`（可后置）

#### 首页关键展示

- 当前用户名称。
- 最近一次面试时间。
- 当前目标岗位。
- 能力树概要：强项、薄弱项、待提升树枝数量。
- 推荐下一步：继续面试、补齐简历、查看复盘。

#### 验收标准

- 登录成功后默认进入工作台。
- 用户可以从工作台选择进入面试或能力树。
- 工作台不依赖模型调用，离线也可打开。

### 5.3 面试前配置流程

#### 目标

让用户在进入面试前明确选择训练目标，而不是直接进入固定岗位面试。

#### 配置项

- 选择简历/Profile。
- 选择目标 JD/岗位。
- 选择面试模式：
  - 文本低成本模式。
  - 文本云端模型模式。
  - 实时语音模式。
- 选择面试强度：
  - 轻松热身。
  - 标准技术面。
  - 压力追问。
- 选择面试时长：
  - 5 分钟快速练习。
  - 15 分钟标准练习。
  - 30 分钟完整模拟。

#### 验收标准

- 面试页启动前必须创建一个 interview session。
- session 中保存用户、profile、JD、模式、强度、时长。
- 面试官开场问题根据用户选择变化。

### 5.4 能力树/知识树模块

#### 命名建议

产品层面建议使用“能力树”，因为它更贴合面试评估；“知识树”可作为能力树中的一个分支类型。

能力树包含：

- 技术知识：算法、系统、框架、领域知识。
- 工程能力：调试、部署、稳定性、指标意识。
- 项目证据：真实项目、职责、量化结果。
- 表达能力：结构化回答、复盘、追问应对。
- 岗位匹配：JD 要求与当前能力的差距。

#### 树枝类型

- 成长枝：最近面试表现变好、有新证据支撑。
- 薄弱枝：回答不清、缺少数据、概念混乱。
- 退化枝：长期未验证或近期表现下降。
- 虚拟树枝：目标岗位需要但当前尚未具备。

#### 页面能力

- 查看总能力树。
- 查看某次面试导致的能力变化。
- 点击节点查看证据：回答片段、评分、面试官追问。
- 查看推荐提升任务。
- 支持按岗位切换目标能力树。

#### 验收标准

- 用户可从工作台进入能力树页面。
- 能力树页面展示当前用户的总能力结构。
- 每次面试报告生成后，能力树有可解释的变化记录。
- 至少能展示成长枝、薄弱枝、虚拟树枝三类。

### 5.5 历史报告模块

#### 目标

让用户回看每次训练结果，形成长期成长记录。

#### 页面能力

- 按时间列出面试记录。
- 展示岗位、模式、时长、总分。
- 打开单次报告。
- 查看本次报告对能力树的影响。

#### 验收标准

- 用户可以看到自己的历史报告列表。
- 报告详情包含摘要、评分、关键证据和改进建议。
- 不同用户之间报告隔离。

## 8. 阶段二优先级

### P0：必须做

- 登录页和基础 session。
- 工作台首页。
- 面试前配置页。
- 用户数据隔离。
- 能力树独立页面。
- 修复前端乱码文案。

### P1：应该做

- 历史报告列表。
- 能力树变化记录。
- 文本/语音模式清晰切换。
- 报告引用 transcript 证据。

### P2：可后置

- OAuth 登录。
- 组织/团队权限。
- 可视化能力树高级交互。
- 正式数据库迁移。
- 云部署后台管理。

## 9. 成功指标

阶段二完成后，应满足：

- 用户进入产品后能清楚选择下一步，而不是被直接带入面试。
- 文本模式、语音模式、能力树和历史报告的入口清晰。
- 每个用户有独立能力树和历史记录。
- 一次面试后，报告和能力树能形成连续闭环。
- 比赛演示时，评委能在 1 分钟内理解产品不是聊天机器人，而是“面试训练 + 能力成长系统”。

## 10. 风险与约束

- 登录系统会引入数据隔离和安全责任，阶段二应先做最小可用，不追求复杂权限。
- 能力树如果做得太重，会拖慢主流程；第二阶段应先做可解释的静态/半交互视图。
- 语音实时链路仍有模型费用和浏览器权限风险，需要保留文本模式作为稳定演示路径。
- 前端视觉可继续交给外部 UI 工具探索，但 Codex 需要负责信息架构、可访问性、状态流和集成质量。

## 11. 第二阶段推荐实施顺序

1. 修复前端乱码和页面文案。
2. 增加前端路由与工作台骨架。
3. 增加轻量登录/session。
4. 引入 user_id 数据隔离。
5. 增加面试前配置页。
6. 把现有面试页改为 session 驱动。
7. 独立能力树页面。
8. 历史报告列表。
9. 联调完整流程：登录 -> 工作台 -> 配置 -> 面试 -> 报告 -> 能力树。
